# Shared inactivity question (#154)

Check-in events travel in the existing durable Activity command outbox (`kind: check_in`) with immutable operation/action/device/sequence fields. The server uses the same singleton transaction lock as all activity mutations. `check_in` in each snapshot holds generation, rearm, armed boundary, known active evidence and one question. It is persisted separately from Actual records. Confirmation never edits time; switch/stop and changed running identity invalidate the question. Old candidates and answers return a durable superseded receipt. Receipt replay returns current state and cannot recreate an answered question.

Web presents the accepted inline hierarchy and confirmation/switch controls. Android uses a dismissible modal with two full-width actions. Its dismissal IDs are durable device-local journal data, independent from the pending shared question. Reopening requires Check-in waiting. Stop remains outside the Android sheet and is absent throughout Focus. Confirmation projects locally only after durable storage and survives restart. Switch/stop projection clears the old question immediately while queued activity intent remains durable.

Off/threshold preferences belong to each installation (15–480 minutes, default 60). Optional sensing permissions never gate recording or mutate another device's settings. This slice explicitly reports sensing not connected; controlled API/adapter events are the review boundary.

## Adapter handoff for #155 / #156

Call the repository `checkIn` with a captured generation and rearm. Capture these when the observation begins; do not restamp old evidence using a fresh snapshot. Candidate/observe fields: capability `supported|approximate|unsupported`, permission `granted|denied|prompt|unavailable`, observed `active|idle|locked|unknown`, contiguous qualified `coverage_start` and `coverage_end`. Approximate capability requires an explained platform signal and real platform validation in the adapter slice. Missing intervals, page visibility, missing interaction and unknown observations do not qualify. Candidates require a full threshold after both the acknowledged armed boundary and latest synchronized active evidence. A newer active observation survives an older offline confirmation. Capability and notification permission are separate, local state; revoke observation coverage when either sensing capability or permission is lost.

The repository attaches local enabled/threshold values to candidate events. Never fabricate device-wide inactivity from an absent application. Use the shared current snapshot to suppress stale generation/rearm work before submitting; the server repeats that guard transactionally. The server never creates candidates on a timer.

Question `id` is the stable notification identity. `candidate_device` and `candidate_operation_id` identify its origin. Only that installation can claim `delivery`, once, using the question ID and generation/rearm. The claim receipt's operation ID must match the stored delivery owner before an OS notification is attempted. Persist a local delivery-attempt/eligibility record before calling the OS, so process death cannot escalate again. Only a locally produced qualifying candidate is eligible; downloading an old question on reconnect is not notification eligibility. Mark initial discovery/old questions consumed locally; never schedule delivery just because a snapshot contains a pending question. A crash after a claim may lose the optional notification, rather than duplicate it. Disconnected cross-device coordination cannot guarantee global knowledge. `notification_dismiss` changes delivery bookkeeping only; the question stays pending. Opening a notification must revalidate its current question identity and navigate to it. Actual platform delivery and eligibility persistence attach in #155/#156.
