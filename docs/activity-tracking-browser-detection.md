# Browser inactivity detection (#156)

The development-gated Activity Tracking host uses native `IdleDetector` only. The adapter feature-detects it and queries its separate permission. Starting tracking from a user gesture requests an undecided detection permission; Settings also offers an explicit request. Denied/revoked/unsupported detection leaves tracking usable. Notification permission is requested separately, only from its Settings button.

A fresh detector uses the configured threshold (15–480 minutes) for idle evidence. Its initial idle state is native evidence of the preceding threshold; a cached property after suspended execution is not. Evidence is clipped to the current live observation session, shared armed boundary and known active evidence. A separate short native threshold (60 seconds) supplies active evidence: `active` means input somewhere within that minute, so only the conservative lower bound (`now - 60 seconds`) is synchronized, never a fabricated exact last-input time. This suppresses another device's longer idle interval without continually postponing the local interval after input ceases. Locked alone supplies no lock duration and cannot qualify. Initial null states wait for the native change event, with a bounded timeout. Unknown states and sensor failures break observation coverage.

Freeze/pagehide, restart/discard, permission loss, preference/generation/rearm changes, and delayed timer execution reset the observation floor. No page-input or visibility inactivity fallback exists. No closed-browser or always-running monitoring is promised. A newly loaded page cannot reconstruct time away. Timers sample while execution is available; they do not themselves establish inactivity.

Only the adapter invocation that durably submits a fresh qualifying candidate can attempt notification delivery. The repository requires an online acknowledgement, matching candidate origin, a durable one-time local attempt, then a server delivery claim whose operation ID matches the returned owner. Offline candidates remain inline and retain original evidence; reconnect/restart never grants notification eligibility. A crash can lose an optional notification rather than duplicate it. Persistent service-worker notifications use the shared question ID as their tag. Dismissal leaves the question pending. Clicking opens Timebox, refreshes current state, validates the ID and navigates to the current Reporting Day; an answered question is not revived. Synchronized answers close stale local notifications even if detection permission was revoked.

The shared Activity repository and app-screen boundaries test qualified evidence, conservative active bounds, full rearming after freeze/revocation, unchanged recording, durable one-time claims and offline replay without notification escalation. Platform verification and final commands are recorded below after review.

Primary platform contracts: [Idle Detection specification](https://wicg.github.io/idle-detection/), [Chrome Idle Detection guide](https://developer.chrome.com/docs/capabilities/web-apis/idle-detection), [Page Lifecycle specification](https://wicg.github.io/page-lifecycle/). These establish native device state and execution limits; they do not identify whether a person continues an offline activity.
